# 企业人才图谱算法设计方案 (GPT)

## 架构概览：分层与可插拔设计

在本方案中，我们采用分层的架构，将人才图谱的分析拆分为独立的模块，每个模块侧重不同维度，可插拔扩展。整体流程如下：

- **数据层**：从MongoDB提取邮件数据，构建沟通网络图（节点为员工，边为邮件往来频次）。这一步建立起组织关系的基础结构。
- **指标层**：在沟通网络上计算硬性数学指标（如中心性、密度、社区等）以及其他可量化特征（如邮件数量、响应时间分布）。这些指标提供可验证的客观度量，是后续分析的基础。
- **AI语义层**：利用本地大模型 Qwen-3 和云端 Gemini，对以上指标和原始内容进行语义增强分析。例如，通过AI对邮件内容主题聚类结果进行命名描述、对关系健康度给出定性判断等。但AI仅在已有指标基础上锦上添花，避免直接让AI"拍脑袋"生成结论。
- **结果集成层**：将各模块输出的指标和分析结果整合为JSON格式的人才图谱画像，供前端展示。每个指标都会附带清晰的业务含义说明，确保结果可解释、易理解。

这种架构下，各分析模块（网络拓扑、关系语义、职能映射、外部生态、风险预警）彼此独立，新增算法时可以作为新模块加入或替换，不影响其他部分。

## 1. 网络拓扑分析：识别信息枢纽与桥梁

**核心问题**：组织中谁是信息枢纽？谁充当团队之间的桥梁？整体协作网络结构如何？

### 算法清单

| 算法 | 定义 | 输入/输出 | 业务含义 |
|------|------|-----------|----------|
| **度中心性** | 节点直接连接的数量 | 网络→每人度值 | 度中心性高的人与很多人直接联系，是信息传播枢纽 |
| **中介中心性** | 通过该节点的最短路径数量总和 | 网络→中介分值 | 充当不同群体间的信息桥梁，离开可能导致信息断层 |
| **接近中心性** | 到所有其他节点平均距离的倒数 | 网络→接近分值 | 能在最短路径内触达所有人，信息传递的快速渠道 |
| **特征向量中心性** | 连接重要人的人更重要 | 网络→特征向量分值 | 识别隐形有影响力人物（可能不发很多邮件但影响力大） |
| **网络密度** | 实际连接数/最大可能连接数 | 团队网络→密度% | 高密度=协作紧密但可能过载；低密度=存在信息孤岛 |
| **社区发现** | Girvan-Newman或Louvain算法 | 网络→社区标签 | 识别非正式组织/社交圈子，发现信息孤岛 |

### 技术实现
- NetworkX 库直接计算
- 结果存入JSON：`{"degree_centrality": {"david@": 0.15, ...}, "communities": {...}}`

## 2. 关系语义分析：识别关系类型与健康度

**核心问题**：不同员工之间的关系性质如何？交流是否顺畅、健康？

### 算法清单

| 算法 | 方法 | 业务含义 |
|------|------|----------|
| **通信频率与互惠度** | 计算双向邮件频次和平衡性 | 高频均衡=强联系；单向频繁=上下级指令关系 |
| **沟通模式分类** | 规则+AI分类 | 识别汇报关系、协作关系、跨部门关系 |
| **情感与语气分析** | NLP情感倾向分析 | 捕捉团队氛围、潜在冲突信号 |
| **语言风格与关键词** | 统计分析用语礼貌程度 | 反映关系亲疏和职能背景 |

### 技术实现
- 互惠度：pandas汇总计算
- 情感分析：TextBlob/VADER/Qwen-3
- 关系分类：规则+AI Few-shot

## 3. 职能映射分析：识别职能领域与人才分布

**核心问题**：公司有哪些核心职能领域？每个人主要贡献在哪些职能？

### 算法清单

| 算法 | 方法 | 业务含义 |
|------|------|----------|
| **主题建模** | LDA/BERTopic | 挖掘潜在主题对应职能领域 |
| **个人职能画像** | 主题分布平均 | 为每人贴上主要职能标识 |
| **职能-网络映射** | 投射到通信网络 | 发现职能筒仓(Silo)或跨职能协作 |
| **AI语义命名** | Gemini自动命名 | 增强可解释性 |

### 技术实现
- Gensim LDA 或 HuggingFace Transformers
- 输出：`{"david@": {"主要职能": "技术协调", "次要职能": ["外部合作"]}}`

## 4. 外部生态分析：外部关系维护与风险

**核心问题**：公司对外有哪些重要关系？由谁维护？是否过于集中？

### 算法清单

| 算法 | 方法 | 业务含义 |
|------|------|----------|
| **内部/外部标记** | 域名识别 | 区分内外通信 |
| **外部联系数统计** | 统计外部组织数和邮件量 | 对外关系广度和深度 |
| **外部关系集中度** | Gini系数/单点依赖分析 | 识别关系过度集中风险 |
| **外部关系类型分类** | 规则+AI | 区分客户/供应商/合作伙伴 |

### 技术实现
- 域名提取：正则表达式
- 单点依赖：bipartite图分析
- 输出：`{"external_contacts": {"david@": 303}, "single_contact_clients": ["BigClientCo"]}`

## 5. 风险预警分析：识别倦怠、离职和单点故障风险

**核心问题**：谁可能工作倦怠？谁有离职倾向？哪些岗位存在单点故障？

### 算法清单

| 风险类型 | 指标 | 判据 |
|----------|------|------|
| **过劳倦怠** | 日均邮件量、深夜/周末发送比例 | 显著高于平均且持续超时工作 |
| **离职倾向** | 邮件量/连接度时间序列下降 | 近期互动急剧减少 |
| **单点故障** | 高中介中心性、独占联系人比例 | 移除后网络分裂明显 |
| **团队协作风险** | 部门内/外密度比 | 信息孤岛、过度依赖主管 |

### 技术实现
- 阈值触发预警规则
- 输出：`{"risks": [{"person": "david@", "type": "burnout", "detail": "..."}]}`

## 实施优先级建议

| 优先级 | 模块 | 理由 |
|--------|------|------|
| **最高** | 网络拓扑分析 | 图谱基础，立刻纠正画像遗漏战略重要性的缺陷 |
| **高** | 外部生态分析 | 对业务风险高度相关，CEO关注度高 |
| **中** | 风险预警分析 | 有了指标后可着手制定风险判据 |
| **中** | 职能映射分析 | 需要验证调整时间，对战略人力规划有帮助 |
| **次** | 关系语义分析 | 精细化锦上添花，短期对高层决策影响较小 |
